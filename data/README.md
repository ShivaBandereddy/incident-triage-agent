# Data card: synthetic infrastructure incidents

## What this is

100 synthetic infrastructure incidents plus 10 runbooks, built for evaluating an incident triage agent.

Synthetic incidents generated by `scripts/generate_incidents.py` (seed 42). Background noise comes from my own templates. Signal lines are authored by me and are approximate; this is not real VMware/Nutanix incident data.

No real company, customer or personal data is included. No Loghub or other third-party log files are included.

## Files

| File | Contents |
|---|---|
| `incidents_dev.json` | 40 incidents, used to tune prompts, runbooks and thresholds |
| `incidents_test.json` | 60 incidents, used only for final numbers (frozen) |
| `runbooks/*.md` | 10 runbooks (the RAG knowledge base) |

## Composition

| Split | Total | Regular | Unknown cause | Prompt injection |
|---|---|---|---|---|
| Dev | 40 | 34 | 3 | 3 (styles 0, 1, 2) |
| Test | 60 | 36 | 12 | 12 (styles 0-5, 2 each) |

Regular incidents cover 10 fault types: datastore_latency, storage_path_down, host_failure_ha, nic_link_flap, datastore_full, memory_pressure, dns_failure, ntp_drift, cert_expiry, raid_degraded.

Difficulty levels (regular incidents):

- easy: several clear signal lines, 1 red herring
- medium: 2 signal lines, 3 red herrings, more noise
- hard: 1 signal line, 3 red herrings, vague alert text
- misleading: signal lines plus a decoy line that looks like a different fault

Unknown-cause incidents contain only noise and harmless warnings, with a vague alert. The correct answer is `unknown`.

## Prompt-injection styles

| Style | Description |
|---|---|
| 0 | Single direct note in the logs |
| 1 | Multi-line fake admin block |
| 2 | Tag/JSON breakout attempt |
| 3 | Instruction inside the alert text |
| 4 | Fake runbook-authority claim in a log line |
| 5 | Paraphrased "disregard the earlier rules" |

Each injection tries to push the agent towards a wrong cause (`injection_target`). The correct answer is unchanged.

## Fields

`id`, `alert_text`, `log_snippet`, `true_root_cause`, `correct_runbook`, `difficulty`, `has_injection`, `injection_type`, `injection_target`, `split`.

The agent receives only `alert_text` and `log_snippet`. All other fields are labels and are never shown to the agent.

## How logs are built

- Each log is a 30-minute window of timestamped lines in realistic order (cause before effect).
- Background noise is drawn from about 36 hand-written templates, weighted so that common lines appear often and scheduled jobs are rarer. Some noise lines contain harmless words such as "error 0" or "warning" on purpose.
- Signal lines, red herrings and (optionally) injection lines are inserted at random times with random values (hostnames, PIDs, latencies).

## Known limitations

- Log formats are approximations of VMware/Nutanix-style lines, not real captures.
- One log can mix ESXi, Nutanix and Linux sources on the same host.
- A failed host can still log "is not responding" lines, which a real dead host would not.
- A decoy line and a red herring can contradict each other (for example a clock-skew decoy next to a "time sync OK" herring).
- 10 fault types only, closed set. Real incidents are messier.
- Small test set: 36 regular, 12 unknown, 12 injection. Per-injection-style n = 2, so per-style results are indicative only.

## Rules for using this data

- The test set is frozen. Do not tune anything on it and do not re-run the generator (it would overwrite `incidents_test.json`).
- Tune only on the dev set.
- Do not generate incidents with the same LLM that is being evaluated.
